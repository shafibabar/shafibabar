What I've built

Observability Copilot · Caizin, client: Smarsh · 2026

An AI reasoning layer on top of the team's Datadog observability stack that turns dashboards into guided, evidence-backed incident investigations. An engineer asks a question in plain language ("why is message processing slow in tenant X?"). The Copilot pulls the relevant telemetry, rebuilds an incident timeline, and reports conclusions sorted into Facts, Hypotheses, Recommendations, and Unknowns, each with a confidence level and a link to the evidence behind it.

It is deliberately not a chatbot and not a dashboard replacement: the dashboard stays the source of truth, and the Copilot interprets it. It is now part of the incident management process, and Support uses it even though it isn't a mandated step.

How it was built: an AI-native development workflow

I conceived, scoped, and directed the initiative as product owner and architect. Claude Code, Anthropic's AI coding agent, did the implementation; I wrote no code by hand. The build ran through formal approval gates:

  1. PlanScope and success criteria
  2. DesignArchitecture and decisions
  3. RoadmapSequenced iterations
  4. Iterative delivery4 iterations shipped

The practices I set up for the build:

  • Strict test-driven development under a "once green, always green" regression rule: 299 automated tests at 98% coverage, about 3.3K lines of application code and 3.8K lines of tests.
  • Decision records (lightweight ADRs), a build log, and version-controlled project-memory files, so any session or machine could pick the work back up.
  • Telemetry on the build itself: a pipeline that measured tokens, prompts, tests, and code changes per prompt and showed them on a dashboard. 66 tracked prompt cycles, about 447M tokens processed.
  • An approval rule: nothing ships without explicit sign-off on any new dependency, security change, or cost change.

Enterprise Conduct pipeline explainer · Caizin, client: Smarsh

An interactive isometric simulation of the Enterprise Conduct pipeline, built over many focused sessions with Claude Code as a pair programmer. It is used with customers to size infrastructure and set performance expectations from their projected daily workloads. The practices carried over:

  • A standing project spec, plus a separate design-decision record that captured why architectural choices were made, not just what was built.
  • Automated checks at every step: syntax validation, an end-to-end smoke test that walks the simulation through every state, and an idle-gating test proving nothing animates without cause (zero changed pixels when paused).

Design and architecture patterns

The layers of Observability Copilot, from data access at the base to what people see at the top. Select or hover a layer to highlight it.

  • Interpret, don't replace. The dashboard stays the source of truth; the AI explains it.
  • Every conclusion carries its evidence. Confidence levels and links back to the telemetry, with Unknowns called out instead of papered over.
  • One set of facts, many audiences. Explanations for five audiences, such as engineer and executive, are built from the same facts.
  • Swappable data sources. A pluggable telemetry layer lets a replay adapter stand in for live Datadog, so demos run against a known incident.

Cost, latency, and quality trade-offs

Two design decisions in Observability Copilot were made for cost and latency:

  • Query less, on purpose. Of about 320 production metric queries, the Copilot queries only the 8 most relevant per question.
  • Cheap checks first. A deterministic filter that costs nothing runs before the LLM classifier, so off-topic and hostile input is rejected before any paid reasoning.

Guardrails and human-in-the-loop for regulated domains

Guardrails built into Observability Copilot:

  • Read-only by design. All Datadog access is read-only.
  • No secrets in the wrong places. Secrets never touch git or the database.
  • Fail closed. If the relevance and abuse classifier can't decide, the request is blocked.
  • Advises, doesn't act. With read-only access it can't change production systems. It reports confidence, evidence, and Unknowns, and the dashboard remains the source of truth.
  • Change control on the build. Any new dependency, security change, or cost change needed explicit approval.
